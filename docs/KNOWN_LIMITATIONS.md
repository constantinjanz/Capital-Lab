# Known limitations

- Docker and the Supabase CLI are required to execute local database/pgTAP tests; application mock mode does not require them.
- The mock weekday calendar is for local fixtures only. Live scheduling must query versioned official market-session rows, including holidays and shortened sessions.
- Vercel snapshot polling is bounded to scheduled decision points and is not a low-latency feed.
- Hosted technical features currently use only the latest 21 eligible completed one-minute bars per feed. They cover spread, short returns, relative volume, five-minute realized volatility, SMA distance, and a documented typical-price VWAP proxy; official-session gap, sector, and broader-market-relative features remain unavailable until the calendar and durable decision-cycle slices exist. Features are derived read-only and are not yet pinned in a persisted decision-context snapshot.
- Free Alpaca IEX coverage is a single exchange and may not represent the full US market.
- Official-source adapters are allowlisted foundations; operators must review each source's current terms, licensing, rate limits, retention, and user-agent requirements before activation.
- Social/political platform adapters, Sol escalation, controlled web research, and weekly AI meta-review are disabled.
- Options, futures, crypto, FX speculation, and other complex assets are non-tradable placeholders.
- Mock embeddings are deterministic test fixtures, not production semantic embeddings.
- The hosted Supabase schema and generated types are connected. Owner-only draft creation uses fixed EUR 100000.00000000 paper-only defaults, durable idempotency, disabled controls, and immutable audit evidence. Draft names/objectives have a separate revision-checked boundary. Locked experiments support only explicit shadow-to-live-paper simulation promotion, pause, resume, completion, and clone-to-disabled-draft; these controls do not start a draft, enable the scheduler/agent, compose proposals into simulated orders, or provide any broker path. Draft-to-replay/shadow start remains unavailable until an owner-reviewed simulator, risk, routing, data-source, prompt/corpus, budget, universe, and official-calendar manifest can be locked atomically. One atomic hosted market statement reads current configuration and owner-scoped evidence at a database-stamped boundary. A separate manual owner action can ingest only the reviewed five-symbol Alpaca IEX quote/completed-bar batch when explicitly configured and enabled; it is not a scheduler or decision cycle. The view is not a historical configuration browser: universe membership is not bitemporal, calendar rows cannot yet represent revisions, and provider-health freshness has no configured threshold. No real OpenAI call or broker call is enabled.
- Protected live Supabase authentication is wired and the confirmed identity is bound as the singleton owner. Application registration/bootstrap, project-level signup, manual identity linking, and anonymous sign-in are disabled; email confirmation remains enabled. Leaked-password protection remains unavailable on the current Supabase Free plan, so the owner should use a unique password; the application does not yet expose MFA enrollment. In Supabase mode, the shell, dashboard landing state, experiment/control list, experiment detail, and market snapshot use owner-scoped hosted reads and never fall back to fixtures. Financial market/detail values and control/draft revisions remain exact strings. Portfolio, cost, and remaining feature pages stay mock/read-only until their precision-safe views and reviewed write use cases replace them.
- The checked-in cron route runs the bounded mock-safe cycle. The database contains official-session, scheduler-lock, idempotency, budget, and pause primitives, but those durable functions must be wired into the runtime cycle after database tests pass. Do not enable a remote scheduler before that review.
- The Luna/Terra/Sol orchestrator, deterministic risk engine, and simulator are tested as separate safe boundaries. Live-paper proposal-to-simulated-order composition is intentionally not enabled until the durable database adapters are connected and reviewed.
- The in-memory manual rate limiter is for single-process local development; a distributed deployment needs database- or platform-backed enforcement.
